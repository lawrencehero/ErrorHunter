| 维度 | 结论 |
|------|------|
| 是否属实 | ✅ 属实 |
| 修复版本 | **MVP（必修）** |
| 法律风险 | 违反《个人信息保护法》第 47 条 + APP 违规认定方法第 3.7 条，可被工信部下架 |
| 工作量 | 3 天 |

**修复方案：**

```
注销入口(UED) → 注销API(Arch) → 数据清理流水线(Ops)
     ↓                ↓                  ↓
  P11个人中心    POST /users/deactivate   7天冷静期后定时清理
  二次确认弹窗    POST /users/reactivate   → DB硬删除
  冷静期7天      Token加入黑名单          → OSS图片删除
                 OSS标记待删              → Redis缓存清理
```

**关键决策：**
- 冷静期 7 天，期间登录自动取消注销
- 冷静期后手机号可重新注册
- 30 天内最多发起 3 次注销
- 已分享的周报长图保留但昵称匿名化
- 注销时需要手机号 + 验证码二次确认

**新增 API：**

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /users/deactivate | 发起注销（需验证码） |
| POST | /users/reactivate | 冷静期内取消注销 |

**冷静期内登录特殊响应：**

```json
{
  "code": 0,
  "data": {
    "status": "DEACTIVATING",
    "recover_before": "2026-06-25T23:59:59+08:00",
    "message": "您的账号正在注销中，登录将自动取消注销"
  }
}
```

**清理顺序（定时任务每日凌晨执行）：**
1. review_records（按 user_id）
2. questions（按 user_id）
3. sync_queue（按 user_id）
4. user_devices（按 user_id）
5. weekly_reports（按 user_id）
6. users（硬删除）
7. OSS 图片目录删除（分批，每次 ≤1000 文件）

### 🟡 严重问题（5 个）

#### #3 Redis KEYS 命令在登录主链路

| 维度 | 结论 |
|------|------|
| 是否属实 | ✅ 属实 |
| 修复版本 | **MVP** |
| 工作量 | 0.5 天 |

**修复方案：改用 Redis HASH**

```
# 现状（危险）
session:{uid}:{device_id} → STRING(sessionJSON)
查找：KEYS session:{uid}:*  ← O(N) 全keyspace扫描

# 修复后（安全）
session:{uid} → HASH { device_id → sessionJSON }
查找：HGETALL session:{uid} ← O(N) 但 N≤3
```

**额外修复：** KEYS 命令的错误不能被忽略，失败时应拒绝操作而非静默跳过。

```go
keys, err := s.redis.HKeys(ctx, fmt.Sprintf("session:%d", userID)).Result()
if err != nil {
    return nil, fmt.Errorf("查询设备列表失败: %w", err)
}
```

#### #4 cached_network_image + OSS 签名 URL 缓存永不命中

| 维度 | 结论 |
|------|------|
| 是否属实 | ✅ 属实 |
| 修复版本 | **MVP** |
| 工作量 | 0.5 天 |

**修复方案（双层）：**

1. **列表页缩略图** → 使用 CDN URL（`img.errorhunter.com`），URL 固定不变，缓存正常
2. **详情页原图** → 使用签名 URL + 自定义 cacheManager（key 去掉签名参数）

```dart
class OSSCacheManager extends CacheManager {
  @override
  Future<File> getSingleFile(String url) {
    final cleanUrl = Uri.parse(url).replace(queryParameters: {}).toString();
    return super.getSingleFile(cleanUrl);
  }
}
```

**边界场景：** 图片更新后缓存可能显示旧图。解决方案：图片 URL 加入版本号 `?v=2`，更新时版本号 +1 使缓存失效。

#### #5 周报批量生成无断点续传

| 维度 | 结论 |
|------|------|
| 是否属实 | ✅ 属实 |
| 修复版本 | **MVP** |
| 工作量 | 1 天 |

**修复方案：聚合 SQL + 分批执行**

```sql
-- 一条SQL算出一批用户的周报（每批1000用户）
INSERT INTO weekly_reports (user_id, week_number, ...)
SELECT user_id, $week_number, ...
FROM questions
WHERE user_id BETWEEN $batch_start AND $batch_end
  AND deleted_at IS NULL
GROUP BY user_id
ON CONFLICT (user_id, week_number) DO NOTHING;
```

- `DO NOTHING` 天然幂等，崩溃重启不重复
- 分批 1000 用户，批间 sleep 100ms
- Go 代码记录批次进度到 Redis，支持断点续传

**运维监控需求：**
- Prometheus gauge：`weekly_report_generation_progress{status="processed|failed|total"}`
- 超过 30 分钟未完成 → P2 告警
- 上线前需压测 10 万用户量级执行时间
